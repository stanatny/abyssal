# Mobile touch and keyboard correction — 2026-10-11

Publication update — 2026-10-11: the user authorizes this accepted revision for commit and main publication in [v0.11.7](release_v0_11_7.md). Candidate-only/uncommitted statements and measurements below retain their historical meaning; they do not block this release or authorize future releases.

The user reports that double tapping sometimes magnifies the phone page without a usable way back, and asks that only entering a result name open the software keyboard. This uncommitted candidate starts from3605bc9 / v0.11.6 on `fix/mobile-touch-keyboard`; main publication is not authorized for this follow-up.

## Diagnosis and change

A fresh390px coarse-pointer Chrome baseline exposes `touch-action: auto` on the document, menu, buttons, Guide and its independent scrollers. Tapping the12px Guide search focuses an editable text field. These are observed input-policy gaps; this desktop run stays at viewport scale1 and does not reproduce the reported physical-phone zoom lock or display its system keyboard.

Apply `touch-action: manipulation` across elements, including top-layer dialogs and nested scrolling surfaces. Existing canvas/joystick `none` and model-preview `pan-y` rules retain precedence. There is no global touchend cancellation, synthetic click, scale-locking viewport tag or extra animation loop. Menus/details retain native scrolling and deliberate pinch zoom. Touch native language/region controls use16px text; the existing result-name input already uses16px. This avoids retaining tiny editable/selection text as another focus-zoom risk.

On primary coarse-pointer devices, hide and disable Guide text search and its label. Clear an old desktop query when changing to touch, and move focus to Close if necessary. Keep region selection, categories, cards and model rotation. Desktop search remains available at any viewport width, including narrow desktop windows. Respond to capability changes and remove the listener on real page disposal; back/forward-cache pages retain it. No new visible copy or translation is introduced.

Result names remain normal text fields with selection, copy/paste and input methods. Opening a result does not focus the name automatically. A successful save blurs it and focuses the save action, ending editing before further browsing. Home/board navigation retains its existing focus management. No gameplay, payment, record semantics, art, audio, population or quality changes.

The gesture policy follows [WebKit's documented fast-tap behavior](https://webkit.org/blog/5610/more-responsive-tapping-on-ios/): manipulation excludes double-tap magnification while retaining panning/pinching. This browser contract supports the implementation, not a claim that every physical browser or embedded webview has been measured. [WebKit's policy predicate](https://bugs.webkit.org/show_bug.cgi?id=319730) also records this distinction.
